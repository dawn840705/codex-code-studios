# Subagent Collaboration Patterns

> 깊은 디자인 / 게임성 / 광범위 결정 영역에 *다수 서브 에이전트 병행 호출* + 결과 통합 패턴. 사람 팀 협업 모사.
> 서브에이전트에게는 사용자 채널이 없다. 질문 대신 **결정 항목**을 돌려받고, 오케스트레이터가
> [`autonomy-contract.md`](autonomy-contract.md) 의 정지 조건 안에서 결정한다.

---

## § 1 — 언제 사용

| 트리거 | 패턴 |
|--------|------|
| **광범위 + 깊은 디자인 결정** (예: 새 시스템 spec) | 다수 서브 에이전트 병행 |
| 단순 기능 / 코드 수정 / 사실 확인 | 메인 Codex 에이전트 단독 |
| 외부 자료 + 내부 spec 통합 | WebSearch + 1~2 서브 에이전트 |

**Rule of thumb**: 결정 영역이 *4+ 분야* 또는 *광범위 게임성 영향* 일 때 → 서브 에이전트 호출.

---

## § 2 — 4 에이전트 병행 호출 패턴

표준 4 분야는 트랙마다 다르다. `PROJECT_TYPE` (SessionStart 훅 출력) 으로 고른다.
팩을 섞지 말 것 — game 프로젝트에 `frontend-engineer` 를, web 프로젝트에
`level-designer` 를 붙이지 않는다 (`$studio-orchestrator`의 트랙 라우팅 참조).

**game 트랙** — 게임 시스템 spec:
1. **game-designer** — 게임 메카닉 / 룰 / 옵션 비교
2. **ux-designer** — 흐름 / 인터랙션 / 게임패드+KBM 정합
3. **ui-programmer** — 구현 아키텍처 / 매니저 / widget spec
4. **gameplay-programmer** — 입력 시스템 / 인터랙트 / 씬 전환 / 백엔드

**product 트랙 (web / mobile / service)** — 기능 spec:
1. **product-manager** — 문제 정의 / 사용자 가치 / 성공 지표 / 비목표
2. **ux-designer** — 플로우 / 인터랙션 / 접근성
3. **frontend-engineer** — 화면 구조 / 상태 관리 / API 연동
4. **backend-engineer** — 데이터 모델 / API 계약 / 권한·정합성

> 4 라는 숫자는 규칙이 아니라 관례다. 분야가 3 개면 3 개를 부른다.
> § 1 의 트리거를 만족하지 않으면 0 개다.

### 호출 절차

```
1. 메인 Codex 에이전트가 안건 분석 → 분야별 spec 명시 → § 2.1 쓰기 소유 표 작성
2. 서로 독립적인 작업만 Codex 서브에이전트로 병행 호출 (§ 2.3)
3. 각 에이전트:
   - 프로젝트 컨텍스트 + 안건 + 결정 권한 영역 + 반환 경계 명시 (§ 3)
   - 소유 경로 안의 산출물은 쓰고, 경로 + 상태 + 되돌리기 명령을 반환 (§ 3.1)
   - 오케스트레이터가 유보한 결정은 결정 항목으로 반환 (§ 3.2) — 질문이 아니다
4. 메인 Codex 에이전트가 결과 통합 → 결정 항목을 autonomy-contract.md 의 정지 조건
   안에서 결정 → 회의록에 기록 (§ 4)
5. K1(권한) 항목만 사용자에게 올린다 (§ 4.3)
```

### Parallel 호출 — 단일 message 안 다수 tool call

병행 호출은 서로 독립적인 조사·검토에서만 사용한다. 같은 파일을 쓰거나 앞 작업의
결과에 의존하면 직렬로 실행한다 (§ 2.2).

```python
# pseudo-code — 역할 가이드를 각각 self-contained task prompt에 포함
spawn_subagent(task_name="game_designer", message="...")
spawn_subagent(task_name="ux_designer", message="...")
spawn_subagent(task_name="ui_programmer", message="...")
spawn_subagent(task_name="gameplay_programmer", message="...")
```

### § 2.1 — 쓰기 영역은 스폰 **전에** 나눈다

병행 호출은 읽기에는 공짜지만 쓰기에는 아니다. **두 에이전트에게 같은 파일을
주지 않는다.** Edit 은 마지막에 쓴 쪽이 이기고, 진 쪽은 자기 변경이 사라진 걸
모른 채 "완료" 를 보고한다. 다른 실패는 어디엔가 흔적이 남지만 이건 남지
않는다 — 통합 단계에서 오케스트레이터가 보는 것은 "둘 다 완료" 뿐이다.

스폰 프롬프트를 쓰기 전에 표를 먼저 채운다. 칸이 비면 그 에이전트는 아직 부를
준비가 안 된 것이다.

| 에이전트 | 쓰기 소유 (이 경로만 Write/Edit) | 읽기만 | 건드리지 않음 |
|---|---|---|---|
| ux-designer | `design/ux/flow-checkout.md` | `product/prd/**` | 코드 전부 |
| frontend-engineer | `src/ui/checkout/**` | `design/ux/**` | `src/api/**` |

- **소유가 겹치면 스폰하지 말고 직렬로 돌린다.** 같은 파일을 두 관점에서 고쳐야
  하면 순서를 정해 하나씩 부르고, 두 번째 에이전트에게 첫 번째의 결과 경로를
  준다. § 5 가 금지하는 직렬 호출은 *독립* 작업에 대한 것이다.
- **소유가 불명확한 산출물이 나오면 작업 전에 소유부터 정한다.** "일단 만들고
  나중에 정리" 는 두 에이전트가 같은 문서의 다른 버전을 각자 진실이라 믿는
  상태로 끝난다.
- 표의 3·4열은 § 3 의 **6. 금지 영역** 에 그대로 복사해 넣는다. 소유 표는
  오케스트레이터의 계획이고, 프롬프트에 들어가야 에이전트에게 구속력이 생긴다.
- 한 에이전트가 여러 파일을 쓰면 **경로 글롭 하나로 묶일 수 있어야** 한다.
  묶이지 않으면 그 에이전트의 작업 범위가 너무 넓다는 신호다.

### § 2.2 — 의존 작업의 협의 순서

크로스 도메인 작업은 앞 단계의 결론이 뒷 단계의 입력이므로 직렬이다. 순서는
"누가 정하고 누가 구현하는가"로 정한다 — 검토는 R3+ 저자≠리뷰어 원칙
([`verify-route.md`](verify-route.md) § 4)이지, 상위 역할의 승인이 아니다.

**game 트랙**:

| 상황 | 협의 순서 |
|------|----------|
| 밸런스 공식 변경 | `systems-designer` → `gameplay-programmer` 구현 |
| GDD 변경 후 구현 | `game-designer` → 해당 도메인 에이전트 |
| AI 행동 변경 | `ai-programmer` 초안 → `systems-designer` 밸런스 검토 |
| UI 플로우 변경 | `ui-programmer` → `game-designer` 정합 검토 |
| 아키텍처 리팩토링 | `lead-programmer` → `technical-director` 검토 → 실행 |
| 성능 최적화 | `performance-analyst` 프로파일링 → `gameplay-programmer` 수정 |
| 스테이지 난이도 조정 | `level-designer` → `systems-designer` 공식 검토 |
| 경제 밸런스 변경 | `economy-designer` → `systems-designer` → `gameplay-programmer` |

**product 트랙**: 같은 원리 — 정의(`product-manager`) → 흐름(`ux-designer`) →
계약(`backend-engineer`) → 화면(`frontend-engineer`). API 계약이 바뀌면 계약 소유자가
먼저 쓰고 소비자가 뒤따른다.

**협의 결과 전달 형식** — 2차 에이전트 스폰 시, 1차 에이전트의 결론을 아래
형식으로 프롬프트에 넣는다 (1차의 반환 본문을 그대로 붙이지 않는다):

```
[{에이전트명} 협의 결과]
{핵심 결론 요약 + 산출물 경로}
---
위 내용을 바탕으로 {구체적 작업 지시}
```

### § 2.3 — 병행 호출 프로토콜

1. 독립 서브에이전트는 **전부 먼저 스폰**하고 그 뒤에 결과를 기다린다
2. 의존 단계로 넘어가기 전에 결과를 전부 모은다
3. 어느 하나가 `BLOCKED` 면 **즉시 표면화**한다 — 조용히 건너뛰지 않는다
4. 일부만 완료되면 **부분 보고**를 낸다 — 완료된 것, 막힌 것, 막힌 이유를 나눠서

## § 3 — 각 에이전트 prompt 의무 항목

각 에이전트는 *자기 conversation* 만 가짐 (메인 Codex 에이전트의 컨텍스트 X). prompt 가 self-contained:

1. **프로젝트 컨텍스트** — 엔진 / 플랫폼 / Phase / 관련 메모리 link
2. **외부 조사 결과** (있다면) — WebSearch 결과 반영
3. **작성 안건** — 각 § 별 명시
4. **결정 권한 영역** — 무엇을 스스로 정하는가(소유 경로 안 산출물, 옵션 선택,
   섹션 초안)와 무엇을 결정 항목으로 돌려보내는가([`autonomy-contract.md`](autonomy-contract.md)
   의 정지 조건: R4·유료 호출·확정 결정 번복·소유 밖 파일·트랙 미확정). 옵션을 제시할
   자리에는 기본값을 선언한다
5. **응답 형식** — § 3.2 완료 보고 형식. 분량 상한은 두지 않는다 — 무엇을 올리고
   무엇을 올리지 않는지는 § 3.1 반환 경계가 정한다
6. **금지 영역** — 읽지 않을 것 / 수정하지 않을 것 / 스폰하지 않을 것
7. **반환 경계** — main context 에 올릴 것 / 올리지 않을 것

### § 3.1 — 6·7 이 왜 의무인가

서브에이전트를 부르는 이유는 병렬화가 아니라 **격리**다. 별도 conversation 을
쓰는 목적은 탐색 과정을 메인 컨텍스트에서 떼어내는 것인데, 6·7 이 없으면
에이전트가 **폐기한 후보와 실패한 시도까지 요약해 돌려보낸다.** 격리하려던 것이
그대로 돌아오면 서브에이전트를 부른 값을 치르고 이득만 잃는다.

**6. 금지 영역** — 무엇을 하지 말지 쓰지 않으면 에이전트는 자기 판단으로 넓힌다.

```
금지:
- 테스트 파일을 수정하지 마세요. 실패는 보고만 하세요.
- design/gdd/ 밖의 문서를 고치지 마세요.
- 다른 서브에이전트를 스폰하지 마세요.
- 사용자에게 질문하지 마세요. 결정이 필요하면 결정 항목으로 반환하세요.
```

리뷰·감사 성격의 에이전트(`qa-lead`, `security-engineer`, `performance-analyst`)
는 **읽기 전용 작업**으로 명시하고 수정 권한을 주지 않는다. 프로젝트가 네이티브
커스텀 에이전트를 함께 운영한다면 `.codex/agents/*.toml`의 샌드박스도 읽기 전용으로
설정한다.

**7. 반환 경계** — 기본값은 아래와 같다. 다르게 하려면 프롬프트에 명시한다.

| 올린다 | 올리지 않는다 |
|---|---|
| 결론과 그 근거 | 결론에 이르는 탐색 과정 |
| 결정 항목 (§ 3.2) — 권고 하나 + 대안 | 검토했다가 버린 후보 |
| 남은 위험 · `BLOCKED` 사유 (K1/K2) | 중간 시행착오, 실패한 시도 로그 |
| **산출물 경로 + 상태 + 되돌리기 명령** | 산출물 본문 전체 |

반환값은 **요약문이 아니라 Artifact 로 낸다** — 파일을 쓴 에이전트는
`production/qa/plan-combat.md — 작성 완료` 처럼 경로와 상태를 돌려주고,
메인 Codex 에이전트가 필요할 때 읽는다. 400 줄짜리 산출물을 대화로 되돌려 받으면
메인 컨텍스트에 그대로 쌓이고, 그 상태로 다음 에이전트를 부르면 § 5 의
"토큰 낭비" 가 팬아웃 배수로 커진다.

### § 3.2 — 완료 보고 형식

에이전트 작업 완료 시 아래 형식을 따른다. 세션 로그(`production/session-logs/`)도 같다.

```
## 완료 보고
- 결론 요약 (bullet) + 근거
- 변경·생성 파일: 경로 — 상태 — 되돌리기 (git checkout -- <path> / 파일 삭제)
- 결정 항목 (있을 경우):
  | ID | 안건 | 권고 | 대안 | 근거 | 되돌리기 비용 (R1~R4) |
- 남은 위험
- BLOCKED (있을 경우): 첫 줄에 `BLOCKED: <무엇>` — K1 권한 / K2 정보 부재만
```

구현 상세, 코드 블록, 긴 설명은 보고서에 포함하지 않는다. **결정 항목은 질문이
아니다** — 권고 하나가 반드시 붙는다. 권고 없는 항목은 오케스트레이터가 서브에이전트의
탐색을 다시 해야 하므로 격리의 이득이 사라진다. "되돌리기 비용" 열이 있어야
오케스트레이터가 § 4.1 에서 결정 주체를 가를 수 있다.

## § 4 — 결과 통합 패턴

에이전트 결과를 받은 후 메인 Codex 에이전트:

### 4.1 결정 항목 표 작성 — 오케스트레이터가 결정한다

서브에이전트가 돌려준 결정 항목을 한 표로 모으고, 항목마다 **결정 주체**를 가른다.
[`autonomy-contract.md`](autonomy-contract.md) 의 정지 조건에 걸리는 것(K1)만
사용자 몫이고, 나머지는 오케스트레이터가 이 자리에서 결정한다. 권고를 따르지
않으면 이유를 적는다.

| ID | 안건 | 권고 | 결정 주체 | 결정 | 상태 |
|----|------|------|-----------|------|------|
| D-1 | … | A | 오케스트레이터 | A 채택 | ✅ |
| UX-1 | … | B | 오케스트레이터 | A 채택 — 사유: … | ✅ |
| A-1 | 유료 API 도입 | A | **사용자 (K1: 비용)** | — | 🟡 대기 |

결정을 미루는 것은 결정이 아니다. 오케스트레이터 몫의 항목이 🟡 로 남아 있으면
통합이 끝나지 않은 것이다.

### 4.2 회의록 작성 — `Documents/Meetings/YYYY-MM-DD-<주제>.md`

회의록 메타 박스 (일자 / 운영자 / 안건 / 결정 채택 상태 / 통합 보고 link / **서브
에이전트 ID 보존**) + § 별 spec 통합 + 4.1 의 결정 항목 표. 메타 박스의 "결정 채택
상태" 는 K1 항목이 남아 있을 때만 🟡 이다. 오케스트레이터가 전부 결정했으면 ✅ 로
쓰고 진행한다.

### 4.3 사용자에게 올리는 것 — K1 항목만, 한 번에

K1 항목은 `production/human-actions.md` 🟡 판단 대기에 적고
([`work-records.md`](work-records.md) § 2), 종료 보고에 묶어 한 번에 올린다.
항목마다 회의록의 결정 항목(권고·대안·근거·되돌리기 비용)을 링크한다 — 사용자가
받는 것은 "골라 주세요"가 아니라 "이렇게 하려는데 막을 이유가 있는가"다.
K1 이 없는 작업은 사용자에게 묻지 않고 § 4.1 의 결정대로 진행한다.

## § 5 — 안티패턴

- ❌ *단순 기능* 에 다수 서브 에이전트 — 토큰 / 시간 낭비
- ❌ 에이전트 prompt 에 컨텍스트 부족 — "based on the conversation" 같은 의존 (에이전트는 새 conversation)
- ❌ 4 에이전트 결과 *복사 붙여넣기* — 메인 Codex 에이전트의 *통합 + 충돌 해소* 책임
- ❌ **독립** 작업의 직렬 호출 (1 에이전트 끝나고 다음) — 병행 호출 vs 4배 느림. 쓰기 영역이 겹치거나 결과가 앞 단계에 의존하면 직렬이 맞다 (§ 2.1, § 2.2)
- ❌ **쓰기 영역이 겹치는 채로 병렬 스폰** — Edit 은 마지막에 쓴 쪽이 이기고, 진 쪽은 자기 변경이 사라진 줄 모르고 "완료" 를 보고한다. 이 목록에서 유일하게 실패가 어디에도 안 남는다 (§ 2.1)
- ❌ **탐색 과정 전체를 서술해 반환** — 오케스트레이터가 내용이 아니라 분량에 설득된다. 긴 서사가 이기는 통합은 통합이 아니다 (§ 3.1 반환 경계)
- ❌ **서브에이전트에게 사용자 질문을 시킴** — 채널이 없다. 질문은 오케스트레이터가 추측하거나 사용자와 왕복하게 만들고, 왕복마다 프롬프트 패키지를 재적재한다. 결정 항목으로 반환 (§ 3.2)
- ❌ **K1 이 아닌 결정 항목을 사용자에게 올림** — 계약 안의 결정은 오케스트레이터 몫이다. 되돌릴 수 있는 선택을 사용자에게 넘기는 것은 신중이 아니라 미룸이다 (§ 4.1)
- ❌ **트랙을 섞어 스폰** — game 프로젝트에 `frontend-engineer`, web 프로젝트에 `level-designer` (§ 2)

## § 6 — 회의록 template

본 패턴의 결과물 = `Documents/Meetings/YYYY-MM-DD-<주제>-Meeting.md` — template 참조:
- `docs/templates/subagent-meeting-template.md` (이 플러그인 안)

회의록 = 결정의 *영구 참조 문서* — 결정 항목(안건·권고·대안·근거·되돌리기 비용) +
결정 주체 + 결정 결과를 모두 보존한다. K1 항목은 사용자 결정이 들어오면 그 자리에
덧붙인다 ([`decision-lifecycle.md`](decision-lifecycle.md) § 2 — 지우지 않는다).
